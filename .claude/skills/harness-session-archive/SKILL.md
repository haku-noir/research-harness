# 会話を残す

## 何が残るか

| もの | 場所 | git | 書くもの |
|---|---|---|---|
| 会話の要約 | `records/sessions/<開始日>_<ID の先頭 8 文字>.md` | 入れる | 本文は Claude。冒頭の `auto` の囲みはスクリプト |
| 会話の一覧 | `records/sessions/README.md` | 入れる | スクリプト |
| 生の記録（JSONL） | `records/sessions/raw/<会話の ID>.jsonl` | 入れない（この PC だけ） | スクリプト（写す） |
| 要約するための読める形 | `records/sessions/raw/digest/<会話の ID>.md` | 入れない | スクリプト |

**読める形の中身**：要約するための材料です。

- 載せるもの：
  - 研究者の発言、Claude の返答の本文、道具の呼び出しの 1 行（時刻と、生の記録の行を探すための uuid つき）
  - 選択肢での質問と研究者の回答。取り消された質問は、回答としてではなく「取り消し」として載せる。
  - 機械が送ったと記録から確かめられる入力は、「ほかの会話・アプリからの入力」として載せる。研究者の発言としては載せない。確かめられるのは、次の二つの形だけ。
    - ほかの会話かアプリが始めた会話の、最初の入力（統括が、起動した作業の会話に送る起動の文など）
    - プログラムが Agent SDK を通して送った入力のうち、SDK で始めた会話の入力と、SDK の実行の最初の入力
  - この入力も、研究者の発言と同じに、会話を記録の対象にし、要約のファイルを作り、まだ要約の無い会話を「要約が要る」にする（切り出した作業の会話を残すため）。数えないのは、「要約した範囲」の後に発言が増えたかを見るときだけ（研究者の発言ではないため）。
  - ほかの入力は、研究者が打っていなくても「研究者」として載り、研究者の発言に数える。アプリが返答を続けるために自分で作った入力や、出どころが記録されていない古い形の行も同じ。そのため、読める形で「研究者」の見出しの下にあることだけでは、研究者が言った証拠にならない（下の「要約を書く」の「決まったこと」）。
  - 承認と決定になるのは、研究者が言ったことだけ（`CLAUDE.md` の「承認と決定」）。「ほかの会話・アプリからの入力」にある承認や決定の言葉を、「決まったこと」の元にしない。
  - 引数の付いたスラッシュコマンド（研究者の発言として扱う）
  - 引数の無いスラッシュコマンド（「研究者のコマンド」として載せる）。研究者の発言には数えない。記録の対象の会話か、「要約が要る」かの判定に入れない（`/exit` や `/clear` で数えないため）。
  - スラッシュコマンドとみなすのは、コマンドの記録そのものだけ。コマンドの印（タグ）を文の中に含むだけの発言は、ふつうの発言として載せる。
  - Claude が作業している間に送った発言は、直前に同じ文を打っていても残す。落とすのは、直後に同じ文がふつうの発言として記録し直されたときだけ（二重に載せないため）。
- 載せないもの：
  - 道具の結果
  - ほかの会話が後から送ったメッセージと、アプリが届ける作業の知らせ。「ほかの会話・アプリからの入力」としても載らない。
- 伏せるもの：メールアドレスと、鍵のような文字列（API キー、トークンなど）。読める形、題、一覧では、置き換えの印に変えて載せる。題を短くするより前に伏せる（短くして切れた鍵の一部が残らないように）。git の URL（`git@<ホスト>:<持ち主>/<名前>` の形）と、`<名前>@<版>` の形の文字列は、メールアドレスとして伏せない。
- 時刻：読める形の冒頭と、要約の冒頭の囲みの「期間」の行に、その時刻がどの時差（UTC からのずれ。`+09:00` など）のものかを書く。この PC の時間帯が変わったら、読める形を作り直す。
- 題：Claude Code がその会話に題を記録していないとき（研究者が付けた題も、AI が付けた題も無いとき）だけ、スクリプトが題を作る。起動の文（`harness-dispatch` の 5）で始めた会話なら、作業の id から作る。どの作業の会話も同じ文で始まり、そのままでは見分けられないため。
- 分岐した会話：同じ発言を二重に載せない。共有する発言は、初めにその発言が書かれた会話に持たせる。
  - その会話が除いた会話（`! <会話の ID の先頭>`）か、対象の外か、この PC に記録の無い会話なら、写しを持つ会話のうち、元にいちばん近いものが持つ。その発言は、その会話の読める形と「期間」に入る。元の会話が戻れば（除くのをやめた、対象に入った、記録がこの PC に来た）、発言も元の会話に戻る。
  - 分岐や再開で、Claude Code が前の会話から写したファイルの始めの部分は、そのファイルの作りから見分ける。CLI で再開した会話では、そのファイルを作った時刻（この PC で分かるとき）も使う。
  - 「分岐元」は、そのファイルを直接作った元の会話（いちばん先の祖先ではない）。その会話が除いた会話（`! <会話の ID の先頭>`）か、この PC に記録の無い会話なら、記録のある会話のうち、さかのぼっていちばん近いもの。
  - 再開した会話（Claude Code が、前の会話の終わりを繰り返す新しいファイルで始めたもの）も、前の会話からの分岐として扱う。二つの会話が互いを分岐元にすることは無い。
  - 分岐で、自分の入力が引数の無いコマンドだけの会話は、「要約が要る」に出ない。

**対象の会話**：

- `hub/session-sources.txt` に書いた作業ディレクトリで開いた会話。ハブと、登録したコードのリポジトリが入る。その下のフォルダとワークツリーを含む。
- 研究と関係ない会話は、`! <会話の ID の先頭>` と書いて除く（後ろに説明を書いてよい）。
  - 除いても、その会話の要約のファイルは残り、記録どうしのリンクにも名前として出続ける。除くときは、統括がその要約のファイルも消す。ただし、ひな形のまま（「要約した範囲」が「（要約待ち）」で、ほかに何も書いていない）のときだけ。git に入っていれば `git rm` で消す。生の記録（`records/sessions/raw/<会話の ID>.jsonl`）と読める形（`raw/digest/<会話の ID>.md`）は git の外なので、消してもよい。だれかが書き込んだ要約は、研究者に聞かずに消さない。
  - 場所を新しくつなぐと、最初にスクリプトが動いたときに、そこで前に開いた会話すべての要約のひな形ができる。研究者が残す会話を選ぶより前にできるので、除く会話は、ひな形をコミットする前に決める。研究者がまだ残すと決めていない会話のひな形は、`chore(sessions):` でコミットせず、先に一覧を示して聞く（下の「要約を書く」の、聞かずに要約しない会話）。そのひな形が残っているあいだは、一覧（`records/sessions/README.md`）もコミットしない。一覧がそのひな形へのリンクを持ち、git に入っていないファイルを指す行が入るため。研究者が選んでからコミットする（除いた会話は、次にスクリプトが動いたときに一覧から消える）。
- パスは引用符で囲んでも、`~` で始めてもよい。注釈になるのは「#」で始まる行だけ。パスの途中の「#」はパスの一部として読むので、パスの行の後ろには説明を書かない。手で動かすと、どの会話にも当たらない行（パスの行も「! 」の行も）を知らせる。二つの PC で使うハブでは、もう一方の PC のパスの行もここに出るが、消さない（`INSTALL.md` の 1-3 の「別の PC でハブを複製し直したとき」の 5）。
- 書くのは、Claude Code の会話を開く場所だけ。ほかの AI の会話はスクリプトが読めないので、その場所を書いても、どの会話にも当たらない行として出るだけ。ほかの AI の会話は、その AI が手で書く要約で残す（`harness/other-ai.md`）。
- ハブのフォルダを移したら、前のパスを `hub/session-sources.txt` に足す。前のパスで開いた会話が、対象の外になるため。
- フックで動くときは、Claude Code が渡す会話の記録の場所も使って、会話を探す。
- 一覧（`records/sessions/README.md`）には、`records/sessions/` にある要約のファイルがすべて載る。この PC に記録の無い会話（別の PC で開いた会話）や、ほかの AI が手で書いた要約も、ファイルから行を作って載せる。題は、ファイルの 1 行目の「# 会話の要約：<題>」から取る（無ければファイルの名前を出す）。前の一覧に行があれば開始の時刻と題はそれを使い、「要約した範囲」の欄は毎回ファイルから読み直す（別の PC で要約を足したときも合うように）。`! <会話の ID の先頭>` で除いた会話は載せない。

**Claude Code が古い会話を消す前に、生の記録を写しておく。** Claude Code は、既定では 30 日使わなかった会話の記録を消す（設定 `cleanupPeriodDays`）。

## スクリプト（自動・手動）

ハブのワークツリーやハブの外から動かすときは、元のハブのパス（`<hub>/.claude/skills/…`）で動かす。

```
python -X utf8 .claude/skills/harness-session-archive/scripts/session_archive.py            （更新）
python -X utf8 .claude/skills/harness-session-archive/scripts/session_archive.py --pending  （更新して、要約が要る会話を出す）
python -X utf8 .claude/skills/harness-session-archive/scripts/session_archive.py --list     （対象の会話を一覧するだけ）
```

- `--list` は読むだけ。ファイルを作らず、書き換えず、ほかの実行を待たせる印（ロック）も取らない。

- ハブのフォルダで開いた会話は、終わるときにフック（`.claude/settings.json` の `SessionEnd`）で自動で更新される。要約は書かない。
- スクリプトがすること：
  1. 生の記録を写す。
  2. 読める形を作る。
  3. 要約のファイルが無ければ、ひな形（「要約待ち」）を作る。一度できた要約のファイルの名前は、その後は変えない（時間帯や、分岐の元の会話が変わっても）。名前を変えると、ほかの記録からのリンクが切れるため。
  4. 要約の冒頭の `auto` の囲みを書き直す（会話の ID、期間、生の記録への参照、その会話でのハブのコミット）。
  5. 一覧に「要約が要る」の印を付ける。
- **スクリプトが変わった後（ひな形の更新の後など）に初めて動くときは、すべての会話を一度読み直す。** いつもより時間がかかる。
  - 前からある要約の冒頭の囲みの「期間」と「分岐元」の行と、読める形が変わることがある。要約のファイルの名前と、人や Claude が書いた本文は変わらない。変わり方は次の二つ。
    - 「期間」の行に時差（`+09:00` など）が付く、または時差の書き方だけが変わる。これだけなら、確かめ直さなくてよい。
    - 「期間」の日時か「分岐元」の行が変わる。直した発言の持ち主の決め方（上の「分岐した会話」）で、発言を持つ会話が変わったため。
  - 書いてある要約（「要約待ち」でないもの）のうち、二つ目に当たるものだけを、統括が研究者に伝え、その要約の本文を新しい読める形と照らして確かめ直す。本文が、いまはほかの会話に持たせた発言を元に書かれていることがあるため。
  - 当たる要約の一覧は、スクリプトは出さない。`git diff -- records/sessions/` で、要約のファイルの「期間」と「分岐元」の行を見る。変わったのが「期間」の行の時差だけの差分は飛ばす。
- **写した生の記録を消しても、Claude Code の会話の記録が残っていれば、次に動いたときに写し直す。**
- **会話の ID の先頭 8 文字が、二つの会話で同じとき**：要約のファイルの名前が重なるので、先に見つかった会話だけに要約のファイルを作る。もう一方には作らず、知らせる（どちらが先に見つかるかは、開始の順とは限らない）。
- **冒頭の囲みを書き直すのは、次のすべてに当たるときだけ。** 囲みが最初の「## 」の見出しより前にある。始まりと終わりの印がそろっている。中がスクリプトの書く行だけ。当たらなければ、そのファイルは触らずに「冒頭の囲みが崩れている」と知らせる。囲みを直せば（印をそろえ、書き足した行を囲みの外に移す）、次から更新される。
  - ただし、記録の対象の会話の要約に、囲みの印の行が一つも無いとき（始まりの印も終わりの印も無い）だけは、題の行の下に新しい囲みを入れる。ほかは変えない。印の行が片方だけ残っている（始まりか終わりの一つだけ）、中に書き足した、といった囲みは「崩れている」として、触らずに知らせる。
- **二つの PC で、同じハブを git で行き来するとき**：
  - 一覧（`records/sessions/README.md`）は、`.gitattributes` の `merge=union` で、両方の PC の行を残してマージされる。重なった行は、次にスクリプトが動いたときに作り直される。
  - もう一方の PC の変更をマージしたら、コミットの前に、このスクリプトと `harness-record-links` のスクリプトを動かす（README の「構成」の二つの PC の段）。
  - スクリプトが書く囲みの中に、git の衝突の印（`<<<<<<<` から `>>>>>>>` まで）がそろって入っていれば、その囲みを作り直す。衝突が囲みの印の外まで続いているときは、「冒頭の囲みが崩れている」と知らせて触らない。先に手で衝突を直す。
  - マージで冒頭の囲みが二重になったとき（始まりと終わりの印が二組ある）も、「崩れている」と知らせて触らない。どちらを残すかを人が決めて、一つに直す。
  - 「要約が要る」の印は、その会話の記録がある PC が付けたものを残す。会話の記録の無い PC で動かしても、印は消えない。
- 読めない要約のファイル（UTF-8 でない、開けない）は触らずに飛ばし、ほかの会話を続ける。一覧に「読めない」と出し、手で動かしたときに知らせる。UTF-8 で保存し直せば、次から更新される。
- 生の記録の壊れた行や、処理に失敗した一つのファイルは飛ばし、ほかを続ける。一つの失敗で全体を止めないため。
- 途中で止められた実行が残した一時ファイル（`.gitignore` の `.*.tmp` に当たるもの）は、次に動いたときに片づける。
- 手で動かしたときに Python が 3.10 より古ければ、そう知らせて止まる（フックは古い Python では何もしない）。
- 「要約が要る」とは、次のどちらか。
  - まだ要約が無い。
  - 「要約した範囲」の後に、研究者の発言か選択肢の回答が増えた（Claude の返答と、「ほかの会話・アプリからの入力」は数えない）。

  対象の外になった会話（その場所を `hub/session-sources.txt` から消した）は、要約のファイルが残っていても「要約が要る」に出ない。

## 要約を書く（Claude）

**だれが書くか**：

- **作業セッション**：報告するとき（`harness-report`）に、自分の会話の要約を書くか、続きを足す。自分の会話がいちばんよく分かっているため。
- **統括**：次の二つのときに、`--pending` に出た会話を要約する。いま動いている会話は除く。
  - 統括として始めたとき
  - 報告を受けたとき（`harness-dispatch` の 6）

  聞かずに要約するのは、いまの作業に属する会話（統括が切り出した作業の会話と、前の統括の会話）だけ。場所を `hub/session-sources.txt` に足すと、そこで前に開いた会話が日付によらずすべて出る。場所をつなぐより前の会話や、数件より多く出たときは、要約せずに一覧を研究者に示し、会話ごとか、まとまりごとに、要約する・要約しない（下の「要約しない会話」）・研究と関係ない（`! <会話の ID の先頭>` で除く。要約のファイルの扱いは上の「対象の会話」）のどれにするかを聞く（`harness/roles/orchestrator.md` の「始めるとき」）。
- **いま動いている会話**：`--pending` には、統括自身の会話と、動いている作業セッションの会話も出る。どちらも統括は要約しない。
  - 動いている作業セッションの会話は、その作業セッションに任せる。
  - 統括自身の会話の要約は、次の統括が書く。ただし、研究者が統括の会話で決めた・確かめた決定を `hub/decisions.md` に書いたときは、その「決まったこと」を統括が自分で書く（下の「決定と会話をつなぐ」、`harness/roles/orchestrator.md` の「統括の仕事」）。作業の会話で決めた決定は、その作業の会話が自分の要約に書く。

**要約しない会話**：研究者が要約しないと決めた会話（研究と関係が薄い、過去の会話のうち主なもの以外など）は、要約のファイルの「要約した範囲」の行を「- 要約した範囲：要約しない（理由）」にする。生の記録は残り、「要約が要る」の一覧に出なくなる。

**書き方**（要約のファイルの `auto` の囲みの下を書く。囲みの中は書き換えず、囲みより前に「## 」の見出しを置かない）。要約のひな形は `harness/templates/session-summary.md`。研究の層の `hub/templates/session-summary.md` があれば、スクリプトはそちらで新しい要約を作る：

```
- 要約した範囲：〜 YYYY-MM-DD HH:MM +09:00（この時刻までの発言を要約した。時差はスクリプトが出したとおりに写す）

## 何をした会話か
（2〜4 行。依頼の中心と、行き着いたところ）

## 流れ
- MM-DD HH:MM［論旨・文献・実装・解析・発表・相談・決定・試行・ハーネス］研究者の依頼と、その結果を 1 行
（日付の順。会話が続いたら、下に足す）

## 決まったこと
<a id="d-YYYYMMDD-HHMMSS"></a>
- **YYYY-MM-DD HH:MM** 決定の内容。決めた人：研究者 / 指導教員 / 両者。生の記録：uuid `<先頭 8 文字>`

## 未決のまま残ったこと
- （その会話の終わりの時点で）
- 会話が自分で置いた値：内容（研究者が確かめる）

## 作ったもの・変えたもの
- ファイル、コミット、ブランチ、セッション

## 関連
- 相談：[<フォルダ名>](../meetings/<フォルダ名>/README.md)
- 文字起こし：[<題>](<../../chats/<ファイル名>>)
- 実験：[<id>](../experiments/<id>/README.md)
```

- **「要約した範囲」の時刻**：要約した最後の発言の時刻を、スクリプトが出した形のまま、時差（`+09:00` など）ごと写す（例：`- 要約した範囲：〜 2026-03-10 00:10 +09:00`）。`--pending` は、最後の発言の時刻を時差つきで出す。時差があれば、時間帯の違う PC でも正しく比べる。時差が無い行（前に書いた要約など）は、その PC のいまの時間帯の時刻として読む。
  - 時差として読むのは、時刻の後ろに空白を置いて書いた `+09:00`・`+0900`・`+09`・`Z` と、それを括弧で囲んだもの（例：`(+09:00)`）。符号は全角で書いてもよい（全角のマイナスも、マイナスとして読む）。
  - 符号の付いた「時:分」を時差として読むのは、実際にある時差のときだけ。そのため `10:00 -11:30` の `-11:30` は時差として読まない（`-11:30` という時差は無いため）。時間の幅としても読まず、終わりは 10:00 になる（`-` を幅の印として読むのは、前後に空白があるときだけ）。`10:00-11:30` も同じで、終わりは 10:00。幅は「〜」で書く（`10:00 -05:00` のように、実際にある時差と同じ形の幅は、時差として読まれるため）。両端とも日付から書くのがよい（例：`2026-03-10 10:00 〜 2026-03-10 11:30 +09:00`。最後の日時を、要約した範囲の終わりとして読むため）。終わりを時刻だけで書いたとき（例：`2026-03-10 23:30 〜 00:10 +09:00`）は、始まりと同じ日の時刻として読み、始まりの時刻より前（時差も入れて比べる。終わりに秒が無ければ始まりの秒は見ないので、`23:30:15 〜 23:30` は同じ日）なら、次の日の時刻として読む（両端の時差が違うときは、始まりから後ろの最初のその時刻）。
- **「決まったこと」に書くのは、研究者か指導教員が決めたものだけ。** 決めた人は研究者・指導教員・両者のどれか。`hub/decisions.md` の決定がここの印にリンクするため。会話が自分で置いた値（報告の「決まったこと」に「自分で置いた値」とあるもの。初期値、仮の定数など）は「未決のまま残ったこと」に、自分で置いた値で研究者が確かめるものとして書く。研究者が確かめたら、確かめた発言の時刻と uuid で「決まったこと」に足す。
  - 決定や承認として書く前に、その言葉が研究者自身のものかを確かめる。読める形で「研究者」の見出しの下にあっても、アプリやプログラムが送った入力のことがあるため（上の「読める形の中身」）。中身の無い「続けて」のような行だけでは、承認にならない（`CLAUDE.md` の「承認と決定」）。
- **時刻と uuid**：「決まったこと」の時刻と uuid は、決めた発言か選択肢での回答のもの。読める形の `<!-- uuid: … -->` から取る。印 `d-…` は、その時刻から作る。同じ秒が重なったら `-2` を足す。
- **続きを足すとき**：読める形の「要約した範囲」より後の部分だけを読み、次のようにする。
  - 「流れ」「決まったこと」「未決」「作ったもの」に足す。
  - 未決が解けたら、そう書き換える。
  - 「何をした会話か」は、範囲が広がったら直す。
  - 最後に「要約した範囲」を、読んだ最後の発言の時刻に直す。時刻は時差ごと写す（上の「「要約した範囲」の時刻」）。
- **長い会話**：読める形を区切って読む。研究者の発言と選択肢の回答を中心に読み、Claude の返答は、決定や結果を確かめるところだけ読む。
- **要約は履歴の記録**：書いた決定はその時点のもの。現在の決定は `hub/decisions.md` に書く（この要約の決定へのリンクを「会話」の欄に付ける）。
- **関連**：その会話で扱った相談・文字起こし・実験を、クリックできるリンクで書く（書き方は `harness-record-links`）。逆向きのリンクは `harness-record-links` が作る。末尾の「この記録を指しているもの（自動）」は書き換えない。
- **書かないもの**：
  - 会話に無いこと
  - 推測（推測を書くなら「推定」と明記する）
  - 長い引用。引用は短い句だけにする。

## 決定と会話をつなぐ

1. **コミットに会話の ID を入れる。** ハブでコミットするときは、説明の最後の `Hub-Agent:` などの行（`CLAUDE.md` の「現在の文書と履歴」）に、次の行を含める。値は環境変数 `CLAUDE_CODE_SESSION_ID`。スクリプトは、この行で会話とコミットを結ぶ。

   ```
   Hub-Session: <会話の ID>
   ```

2. **決定に会話を付ける。** `hub/decisions.md` の決定の「会話」の欄に、決めた会話（統括の会話か、作業の会話か）の要約の「決まったこと」の印へのリンクを書く（`harness/roles/orchestrator.md` の「決定を書いたら、決めた会話の要約とつなぐ」）。

   ```
   - 会話：../records/sessions/2026-01-10_1a2b3c4d.md#d-20260115-143000（`hub/decisions.md` からの相対リンク）
   ```

   決めた言葉そのものは、要約の uuid で生の記録（または読める形）を探して確かめる。

3. **会話の記録の更新のコミット。**
   - 自分の会話の要約は、報告や決定と一緒に、ふつうのコミットでコミットする（`Hub-Session:` の行を付ける）。
   - `chore(sessions):` は、自動の更新（`auto` の囲みと一覧）と、ほかの会話の要約を書いた・足したときに使う。新しくできた要約のひな形のうち、研究者がまだ残すと決めていない会話のもの（場所を新しくつないで出た前の会話）は含めない。そのひな形が残っているあいだは、`records/sessions/README.md` も含めない（上の「対象の会話」）。件名は `chore(sessions): <自動の更新か、どの会話の要約を書いた・足したか>` にする（`CLAUDE.md` の「現在の文書と履歴」の例外）。
   - `chore(sessions):` のコミットには、`Hub-Session:` の行を付けない（`Hub-Agent:` などの行は付ける）。
   - このコミットは、要約の「ハブのコミット」の一覧に載らない。載せると、要約を更新するたびに一覧が変わり、更新が終わらないため。

## 秘密

- 会話の記録は研究の中身そのもの。ハブの外（ウェブ検索、外部のサービス、コードのリポジトリ）に出さない（`CLAUDE.md` の「ハブを公開しない」）。
- 生の記録と読める形は git の外で、この PC にだけ残る。要約から生の記録を参照できるのは、この PC の上だけ。
