# 作業を切り出す

統括のセッションで使います。目的は、作業セッションが最初に指示書を読むだけで、「何の研究の、論旨のどこのための、どんな作業か」が分かるようにすることです。

## 1. 目的を確かめる

次の三つが、研究者の言葉、`hub/state.md`、論旨の正本から読み取れるかを確かめます。読み取れないものだけを研究者に聞きます。

- **何を作る・確かめるか**
- **研究の中での位置**：論旨のどの主張・仮説・未決のためか。どの実験か。
- **終わったら次に何ができるか**：この作業の結果で何を決めるか。

研究者が「試してから本流に入れるか決めたい」と言っている、または結果しだいで扱いが変わる作業なら、種類を「試行」にします。

## 2. 種類と場所を決める

| 種類 | 手引き | 作業の場所 |
|---|---|---|
| 論旨 | `harness/roles/argument.md` | ハブ（`papers/<論文の id>/`。指示書にどの論文かを書く） |
| 文献 | `harness/roles/literature.md` | ハブ（`literature/` か、プロフィールの場所） |
| 実装 | `harness/roles/implementation.md` | コードのリポジトリ |
| 解析 | `harness/roles/analysis.md` | 解析のリポジトリかディレクトリ |
| 発表 | `harness/roles/slides.md` | ハブ（`slides/`） |
| 試行 | `harness/roles/trial.md` と、確かめる内容の種類の手引き | 試行のブランチ、または下書きの場所 |
| レビュー | `harness/roles/review.md` | ハブの外の、何も無いフォルダ（`hub/profile.md` の「場所」。無ければ研究者に聞いて作る）。読むだけで、見る対象の場所は指示書に書く |

- **id を付ける。** `<種類>-<短い名前>`（`hub/workstreams.md` の例を見る）。
- **担う AI を決める。** 研究者が別の AI を指定しなければ、統括と同じ AI。`hub/profile.md` の「使う AI」の表に無い AI なら、指示書を書く前に研究者に聞く（`CLAUDE.md` の「ハブを公開しない」）。表にあっても、その AI の「役」（統括 / 作業 / レビュー）がこの作業を含まなければ（レビューならレビュー、ほかの種類なら作業）、研究者に聞く。初めて作業させる AI なら、起動の文に「先に `<hub>/harness/other-ai.md` の「初めて作業の会話として使われたとき」を読む」を添える。
- **論旨を大きく変える作業なら、ハブのワークツリーを作る。** `git worktree add .claude/worktrees/<名前> -b <ブランチ>` で作り、指示書の「作業の場所」に、そのパスとブランチを書く。コミットの置き場所とマージの仕方は、`harness/roles/argument.md` の「大きな改訂のブランチ」。
- **重なりを確かめる。** `hub/workstreams.md` で、同じファイルを触る作業が進行中でないか確かめる。重なるなら、順番にするか、ワークツリー（別の作業コピー）で分けるかを研究者に聞く。

## 3. 指示書を書く

`harness/templates/brief.md` を写して `hub/briefs/<id>.md` を作り、埋めます。

- **写さずに場所で示す。** 論旨や文字起こしの中身を指示書に写さない。読むべき節とファイルを場所で示す。指示書が古くならないようにするため。
- **渡してよいものか確かめる。** 「最初に読むもの」と「レビューの観点と渡す情報」に挙げたものが、担う AI の「渡さないもの」（`hub/profile.md` の「使う AI」の表）に当たらないかを確かめる。当たれば、指示書に書く前に研究者に聞く。
- **決まっていることと、決まっていないことを分ける。** 決まっていないことは「研究者に聞く」と書く。統括が推測で決めない。
- **指導教員の指摘に対応する作業なら、相談の記録と文字起こしを書く。** 指示書の「関わる相談」に書き、作業の会話には報告の「関連」にも書かせる。相談の記録の末尾に、対応した作業が自動で並ぶようにするため（`harness-meeting-record`）。
- **レビューなら、観点と渡す情報を研究者に確かめる。** 統括が案を出し、研究者が決めてから指示書に書く（`harness/roles/review.md`）。読ませる資料は、指示書の「レビューの観点と渡す情報」と「最初に読むもの」の 3 の両方に、同じに書く。レビューの会話が読むのは、研究の中身としてはそれと指示書だけ、手順としては `harness/roles/review.md` の「起動と読むもの」にあるものだけ。同じ AI の新しい会話に任せてもよい。
- **レビューなら、「守ること」のレビューの行を残し、秘密を写す。** レビューの約束の行は、ひな形の文のまま残す。「レビューで守る秘密」に、`hub/profile.md` の「秘密」から、この作業に関わるものを写す。レビューの会話はプロフィールを読まないため（`harness/roles/review.md` の「起動と読むもの」）。レビューでなければ、その行を消す。
- **完了の条件は、確かめられる形で書く。**
- **秘密を書く。** 作業の場所がコードのリポジトリなら、公開でも非公開でも、書いてはいけないもの（ハブの中身）を書く。

## 4. 記録する

- `hub/workstreams.md` に 1 行足す（状態：準備）。`hub/state.md` の「進行中の作業」の表にも、同じ作業を 1 行足す。二つの表は、作業の行と状態をそろえておく。
- **新しい実験の作業なら、実験の記録を作る。** `records/experiments/<id>/README.md` を `harness/templates/experiment.md` から作り、「目的」と「設計」を埋め、「状態」を置く（その後は、実験の作業の会話が報告のときに直す）。実験の id は `exp-` で始める（例：`exp-pilot`。記録どうしのリンクが名前で探すため）。
- 指示書と一覧（`hub/workstreams.md` と `hub/state.md`）をコミットする。新しい実験の記録を作ったなら、それも同じコミットに含める（説明：「`<id>` を開始」と目的。きっかけがあればファイル名）。
- **初めての場所なら、つなぐ。** 研究者に確かめてから行う。
  - 作業の場所がハブの外なら（データだけを置くフォルダ、レビューの何も無いフォルダも）、`hub/session-sources.txt` に 1 行足す。足さないと、そこで開いた会話の生の記録は写されず、要約のファイルも作られない（報告の手順の「自分の会話の要約を書く」ができない）。
  - コードのリポジトリで `CLAUDE.local.md` がまだ無ければ、`harness-install` の「6. コードのリポジトリとつなぐ」も行う。レビューのフォルダには `CLAUDE.local.md` を置かない（`harness/roles/review.md`）。

## 5. 起動する

起動の文は、どの道具でも次の 1 文です。

> `<hub>/hub/briefs/<id>.md` を読んで、その指示に従って始めてください。

- **新しい会話を、作業の場所で始める。** 統括の会話の文脈を引き継がない。指示書だけで分かるようにするため。
- **レビューなら、ハブの外の何も無いフォルダで開き、指示書の要約を添えない**（`harness/roles/review.md` の「起動と読むもの」）。
- **起動の仕方は、道具ごとの補足に従う。** Claude Code（デスクトップ版・CLI）は `harness/claude-code-notes.md` の「作業の会話を起動する」。ほかの AI は、導入のときに作った読み替えに従う。統括が起動できない道具なら、起動の文を研究者に示し、研究者が新しい会話を開いて送る。
- 起動したら、`hub/workstreams.md` の状態を「進行」にし、セッションの名前か id を書く。`hub/state.md` の「進行中の作業」の状態も「進行」にする。そしてコミットする（4 でつないだときの `hub/session-sources.txt` の変更も含める）。

## 6. 報告を受けたら

作業の会話が区切りに来たことが分かったときに行います。どう分かるかは道具によって違います（`harness/claude-code-notes.md` の「作業の会話が終わったことを知る」）。研究者が「終わった」と言ったときも行います。

1. `hub/reports/<id>.md` の最新の節を読む。
2. **報告は証拠ではない。** 証跡を確かめる。
   - 差分（`git -C <場所> status`、`log`、`diff --stat`）
   - テストの結果のファイル
   - 図
   - 書いたと言っているファイル

   確かめられなかったことは「未確認」と伝える。
3. 現在の文書を更新する。
   - `hub/workstreams.md`：状態。完了・中止した作業は行を消す。`hub/state.md` の「進行中の作業」の表も同じに直す（状態を直す、終わった作業の行を消す）。
   - 決まったことがあれば `hub/decisions.md`。古い決定は書き換える。書くのは、研究者か指導教員が決めたものだけ。作業の会話が自分で置いた値（報告の「決まったこと」に「自分で置いた値」とあるもの）は、確かめる項目として研究者に示し、研究者が確かめるまでは未決のままにする。
   - 現在地が変わったら `hub/state.md`
   - 報告の「用語集に足すもの」を `hub/glossary.md` に反映する（出典を付ける）。迷うものは研究者に聞く。
   - コミットの説明に、何が進んだか、変わった決定の前と理由を書く。これが履歴になる。
   - 会話の記録を更新し（`harness-session-archive` のスクリプトを `--pending` で）、要約が要る会話を要約する。いま動いている会話（統括自身の会話と、動いている作業の会話）は除く。統括自身の会話の要約は次の統括が書く（「決まったこと」だけは、決定を書いたときに統括が書く。`harness/roles/orchestrator.md` の「統括の仕事」）。作業セッションが自分で要約していれば、それを確かめるだけ。決定を書いたら、その「会話」の欄に、要約の「決まったこと」の印へのリンクを書く。
   - 記録どうしのリンクを作り直す（`harness-record-links`）。切れたリンクが出たら直す。指している記録が報告や作業の会話の要約でも、リンクの先だけは統括が直してよい（`CLAUDE.md` の「ファイルの持ち主」の例外）。要約を書いた後に作り直すので、新しい要約のリンクも入る。
   - 会話の終わりのフックやスクリプトが直しただけのファイル（会話の要約の `auto` の囲み、`records/sessions/README.md`、`records/links.md`、`chats/README.md`、各記録の末尾の囲み）は、`chore(sessions):`・`chore(links):` の件名でコミットする（`Hub-Session:` は付けない）。ただし、自動の囲みや一覧の外も変わっているファイル（動いている作業の会話の書きかけ）は含めない。`git diff` で確かめる。
4. 研究者に、要点を伝える。
   - 確かめたこと
   - 確かめていないこと
   - 作業セッションが研究者の答えを待っているか
   - 作業の会話が自分で置いた値（確かめる項目）
   - 次に決めること
5. 試行なら `harness-merge` に進む。
6. **追加の指示**：同じ作業の続きは、原則として同じ会話に送る。研究者の承認を伝えるときは、研究者の言葉を引用する。送る道具が無ければ、研究者に送ってもらう文を示す。ただし、下の「同じ作業を新しい会話で続ける」に当たるときは、新しい会話を提案する。
7. **作業が終わったら**：会話を閉じるかアーカイブするかを研究者に聞く。研究者が良いと言ったときだけ閉じる。

## 同じ作業を新しい会話で続ける

いまの会話をそのまま続けると、古い文脈のまま進んでしまうときに使う。いつ新しくするかは研究者が決める。統括は、次の場面に当たると気づいたら提案する。

- 間が空いて、その間に決定や現在地が変わった
- 会話が長くなり、何度も要約されて細部が落ちている
- 作業の段階が変わった（例：実装から実験の実施へ）
- 元の会話を閉じた、または別の PC や CLI で続けたい

同じ日のうちの追加の依頼や、直前の作業の手直しは、同じ会話に送る。

**続け方**：

1. 指示書に、新しく決まったことと、続きで行う範囲を書き足す（指示書は統括が書く）。
2. 新しい会話を起動する。起動の文は次のとおり。

   > `<hub>/hub/briefs/<id>.md` を読んで、続きから始めてください。前の会話の報告（`<hub>/hub/reports/<id>.md`）と要約（`<hub>/records/sessions/` の前の会話）も読んでください。

3. 新しい会話は、読んだ後に、前の報告からの変化（`hub/decisions.md` と `hub/state.md`）を確かめ、続きで何をするかを研究者に返してから始める。
4. `hub/workstreams.md` の「セッション」の欄に、前の会話と新しい会話の両方を書く（新しいものを後ろに）。

## 統括が自分でやってよいこと

数回の道具の呼び出しで終わるもの（短い読み取り、記録の更新、一つの小さな修正）は、切り出さずに統括で行ってよい。切り出すかどうか迷ったら、次で判断する。

- 作業の結果が、ブランチ・版・図・資料のような「それ自体の成果物」になるなら切り出す。
- 統括の会話の文脈に頼る短い作業なら、統括で行う。
