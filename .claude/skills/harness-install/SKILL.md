# 研究ハブの導入

INSTALL.md の「1. ハブを取得する」が済んでいる前提です。以下の `<hub>` はハブのフォルダの絶対パスです。

この会話がハブの外で動いているなら、先に `<hub>/CLAUDE.md` を読み、その約束（コミットの説明の形など）に従います。ハブの外では自動で読み込まれないためです。

Claude Code 以外の AI が導入するときは、`harness/other-ai.md` の「3. 読み替えを作る」も行います。

## 守ること

- **元の資料を動かさない。** 研究者の許可なく、移動・削除・書き換えをしない。取り込みの既定は「写す」か「参照（場所を記録するだけ）」。
- **聞いてから決める。** 質問は一度に 3 つまでにし、選択肢と推奨を付ける。答えが無い項目は「未決」と書いて残し、推測で埋めない。
- **研究の中身を外に送らない。** 読んだ内容を、ウェブ検索や外部のサービスに送らない。
- **現在の文書には現在の内容だけを書く。** 取り込んだ資料にある古い決定・前の名前・変更履歴は、現在の文書に写さない。経緯は `records/history/` と、取り込んだ git の履歴に残す（`CLAUDE.md` の「現在の文書と履歴」）。
- **組み立てたものは研究者が確かめる。** 現在地・決定・用語集・導入前の経緯を組み立てたら、研究者に見せて直してもらう。履歴から組み立てたものには、解釈が入るため。

## 導入の 2 段

導入は 2 段に分けます。一つの会話で全部を進めると、会話が長くなって何度も要約され、後半の手順が抜けやすいためです。

| 段 | 中身 | 会話 |
|---|---|---|
| 段 1：骨組み | 1〜4、6、7。進行中の研究なら、5.1 で資料の場所を聞き、段 2 の項目を作業の一覧に登録する | 一つの会話で終える |
| 段 2：取り込み | 5.2〜5.4 を、資料の種類ごとの項目に分け、一つずつ行う | 項目ごと。会話が長くなったら、項目の区切りで新しい統括の会話に移る |

- **段 2 の項目は、作業の一覧（`hub/workstreams.md`）に 1 行ずつ載せる。** 種類は「導入」、id は `imp-<種類>`、状態は「準備」。終えた項目は行を消してコミットする。途中で会話が切れても、作業の一覧から続きを始められる。
- **段 2 は統括が行う。** 取り込みは、統括が持つファイル（決定、用語集、相談の記録など）を書くため。
- **研究者に無い資料の項目は、登録しない。**
- **順番**：前の項目の結果を、後の項目が使う。

| 順 | id | 中身 |
|---|---|---|
| 1 | `imp-papers` | 論旨の文書の取り込み（5.2）と、研究の全体像（`hub/research.md`）の初版 |
| 2 | `imp-chats` | 文字起こしの取り込み（5.2） |
| 3 | `imp-meetings` | 相談の記録と、見せた資料（5.3） |
| 4 | `imp-experiments` | 実験の記録（5.3） |
| 5 | `imp-literature` | 文献の一覧（5.3） |
| 6 | `imp-sessions` | 会話の記録と要約（5.3） |
| 7 | `imp-history` | 導入前の経緯（5.3） |
| 8 | `imp-current` | 現在の決定、用語集、進行中の作業、個人の記憶の分け方、研究者が使っているスキル、記録どうしのリンク、現在地の仕上げ（5.3）、確かめる（5.4） |

## 1. 新しい研究か、進行中の研究か

研究者に聞く。

- 新しい研究：2〜4、6、7 を行い、5 は飛ばす。
- 進行中の研究：段 1 で 2〜4、5.1、6、7 を行い、段 2 で 5.2〜5.4 を行う（上の「導入の 2 段」）。

## 2. 研究の基本（`hub/profile.md`）

`harness/templates/profile.md` の項目を聞きます。

1. 研究者の呼び方、研究の題（仮）、種類（修論など）、文書の言語
2. 指導教員の呼び方、所属（任意）、期限（提出日、次の発表）
3. 使っている道具（Claude Code のデスクトップ版か CLI か、外部のスキル、発表資料の形式）。導入している AI を、プロフィールの「使う AI」の表の最初の行に書く。ほかにも使う AI があれば、ハブの中身を渡してよいかを研究者に聞き、許可されたものを足す。
4. 研究の問い（1〜3 行。決まっていなければ空欄でよい）。`hub/research.md` の「研究の大きな問い」に書く。
5. いま書いている論文（無ければ「まだ無い」でよい）。論文ごとに、次を聞く。
   - 論文の id（例：`2027-master-thesis`、`2026-conference-x`）、種類、提出先・投稿先、期限
   - 研究全体のどの問いを扱うか
   - 文書の組。次から選んでもらう。答えが無ければ「論旨だけ」。
     - 論旨だけ（`argument.md`）
     - 論旨、骨子、本文の仮組（修論・博論のような長い文書）
     - 研究者が挙げる組

## 3. 公開範囲とコミット

1. ハブの git をどうするか。
   - 手元だけ（推奨）
   - 非公開のリモート：研究者がリポジトリを作り、URL を教えてもらう。
     1. `git remote add origin <URL>`
     2. 非公開であることを確かめる。GitHub なら `gh repo view <owner/name> --json visibility` が `PRIVATE`。確かめられなければ、研究者に GitHub の画面で確かめてもらう。
     3. 研究者自身に、`git config --add hub.pushAllowed origin` を実行してもらう。
   - push の守り（`INSTALL.md` の 1-3）が入っていることも、ここで確かめる。
2. ハブの控えを取るか（既定：取らない）。
   - 取るなら、取り方と置き場所を研究者が決める（例：外付けのディスクやクラウドのフォルダに `git bundle`、非公開のリモート）。いつ取るかも研究者が決める。
   - git の外のもの（会話の生の記録、文献の原文、実験のデータ）は、ハブの git の控えには入らないことを伝える。
   - 決めたことを `hub/profile.md` の「ハブの控え」に書く。
3. `chats/` はハブの git に入れる。記録どうしのリンクなど、仕組みが読むため（ハブは手元だけか非公開）。これは聞かずに、研究者に伝えるだけにする。
4. 生の文字起こしを `chats/raw/`（git の外）に残すか。
5. 秘密：外部の検索語やサービス、公開のリポジトリに出さないもの（例：指導教員の未発表の考え）。
6. コミットの方針：聞くのはコードのリポジトリだけ（既定：頼まれたときだけ）。ハブの記録と論旨の正本は、区切りごとにコミットする。履歴の正本はコミットの説明なので、選べない。

## 4. 骨組みを作る

1. フォルダを作る：
   - `hub/briefs/`
   - `hub/reports/`
   - `papers/`
   - `chats/`
   - `records/meetings/`
   - `records/experiments/`
   - `literature/`
   - `slides/`
2. ひな形から写し、答えを埋める（`{{…}}` の箇所）。
   - `harness/templates/state.md` → `hub/state.md`
   - `research.md` → `hub/research.md`（研究の全体像）
   - `profile.md` → `hub/profile.md`
   - `rules.md` → `hub/rules.md`（この研究の決まりを書く骨組み。既定は `harness/base-rules.md` にあり、写さない）
   - `glossary.md` → `hub/glossary.md`
   - `workstreams.md` → `hub/workstreams.md`
   - `decisions.md` → `hub/decisions.md`
   - `literature-index.md` → `literature/index.md`
   - `literature-readme.md` → `literature/README.md`（文献の置き方の案内）
   - `session-sources.txt` → `hub/session-sources.txt`（コードのリポジトリの作業ディレクトリは、6 で足す）
3. 論文ごとの論旨（2 の 5 で挙げた論文ごと）。
   - まだ文書の無い論文（これから書く論文）：`harness/templates/argument.md` → `papers/<論文の id>/argument.md`。冒頭の「文書の組」に、2 の 5 で選んだ組を書き、組の文書（骨子、本文の仮組）があれば同じフォルダに置く。
   - 既存の文書がある論文：ここでは作らず、段 2 の `imp-papers` で取り込む（5.2。別の git で管理している文書は、その履歴ごと取り込む）。研究者が「外に置いたまま使う」と決めたときだけ、`hub/profile.md` に場所を書いて参照にする。
   - `hub/research.md` の「論文」の表に、論文ごとに 1 行足す。

## 5. 取り込む（進行中の研究のとき）

### 5.1 資料の場所を聞く

次の表の種類ごとに、場所を聞きます。分からないと言われたら、候補を探して示します。

- ホームの下の git リポジトリ
- Claude Code の履歴（`python -X utf8 <hub>/.claude/skills/harness-progress-timeline/scripts/claude_history.py --list`）

| 種類 | 例 | 既定の扱い |
|---|---|---|
| 論旨の文書 | 論旨、骨子、序論、メモ | 論文ごとに `papers/<論文の id>/` に置く。別の git で版を管理しているなら、履歴ごと取り込む（5.2）。そうでなければ写す。論文をまたぐ研究全体の内容（大きな問い、位置づけ、分かったこと）は、`hub/research.md` に分けて書く案を研究者に示す |
| 指導教員との記録 | 文字起こし、議事録、レビュー、コメント | `chats/` に写す（元は残す） |
| 見せた資料 | 確認用の PDF、スライド | 見せた相談の `records/meetings/<日付>_<題>/` に写す |
| コードのリポジトリ | 実験のシステム、解析 | 参照。`hub/profile.md` と `hub/workstreams.md` に登録する |
| 仕様書・検証記録 | `docs/*_spec.md` など | 参照。`records/experiments/` に、実験ごとにまとめる |
| データ・図 | 実験のログ、グラフ | 参照のみ（git の外）。所在を `records/experiments/` に書く |
| 文献 | 原文のフォルダ、調査の記録 | 原文は git に入れない。場所を `hub/profile.md` の「文献」に書くか、`literature/<話題>/` に写す（どちらも git の外）。参照の一覧 `literature/index.md` を作る（5.3） |
| Claude Code の履歴 | `~/.claude/projects/` | 読むだけ。導入前の経緯と、現在の決定を確かめる材料にする |
| 個人の記憶・指示 | `~/.claude/projects/<…>/memory/`、個人の `CLAUDE.md` | 読んで、分け方の案を出す（5.3） |

聞き終えたら、場所を `hub/profile.md` に書き、段 2 の項目を作業の一覧に登録します（上の「導入の 2 段」）。段 1 は、ここから 6 と 7 に進みます。

### 5.2 写すときの約束

- `chats/` には、`.md` のファイルとして直下に置く。仕組みが読むのは `chats/*.md` だけのため。下のフォルダは作らない（git の外の `chats/raw/` のほかは）。
- 名前は、拡張子のほかは変えない。`.txt` は拡張子を `.md` にし、`.docx` などは Markdown に直す（元のファイルは残す）。日付が名前に無ければ、ファイルの冒頭か `records/meetings/` に日付を書く。
- 研究者が「移す」と言ったときだけ、元を消す。既定は写すだけ。

**独自の git を持つ文書（論旨の正本など）を取り込むとき**：

その git の履歴をハブの git に取り込み、現在の版を `papers/<論文の id>/` に置きます。他のブランチとタグは、ハブの git の参照として残します（履歴でだけ見える）。

1. 研究者に、どのブランチを「現在の論旨」にするかを聞く。
2. 元の作業コピーがすべてきれいか確かめる（`git -C <元> worktree list`、それぞれの `git status --short`）。
3. git の管理の外にあるファイル（確認用の PDF など）のうち、残すものを確かめる。見せた資料は、場所を控えておき、`imp-meetings` で相談の記録に写す（相談の記録はそこで作るため）。
4. 元のブランチとタグを、ハブの git に取り込む。

   ```
   git fetch --no-tags <元> "refs/heads/*:refs/heads/archive/<名前>/*" "refs/tags/*:refs/tags/archive/<名前>/*"
   ```

5. 現在のブランチを `papers/<論文の id>/` に取り込む（サブツリーの取り込み。履歴はハブの git の履歴に入る）。

   ```
   git merge -s ours --no-commit --allow-unrelated-histories archive/<名前>/<現在のブランチ>
   git read-tree --prefix=papers/<論文の id>/ -u archive/<名前>/<現在のブランチ>
   git commit -F <説明を書いたファイル>
   ```

   論旨の文書が元の git の下のフォルダにあるなら、そのフォルダだけを取り込む（`read-tree` の最後を `archive/<名前>/<現在のブランチ>:<フォルダ>` にする。6 の中身の確かめも、`archive/<名前>/<現在のブランチ>:<フォルダ>` と比べる）。

   コミットの説明には、どのブランチを現在にしたか、他のブランチをどこに残したかを書く。
6. 確かめる。
   - 中身が一致すること（`git diff --stat archive/<名前>/<現在のブランチ>^{tree} HEAD:papers/<論文の id>`）
   - 取り込んだ参照の数
   - `git log <取り込みのコミット>^2`（＝`archive/<名前>/<現在のブランチ>`）で、元の履歴が見えること。`git log -- papers/<論文の id>/` には取り込みより前の履歴は出ない（元の履歴ではファイルが最上位にあったため）。`hub/profile.md` に、取り込む前の履歴の見方を書く
7. 元を消すのは、研究者が確かめてから。消す前に、下の 9 を済ませる。
8. **正本の形に合わせる。**
   - 正本のファイルの名前が `argument.md` でなければ、取り込んだ後に `git mv` で `papers/<論文の id>/argument.md` に直す（別のコミット。前の履歴は `git log --follow` でたどれる）。
   - 冒頭の「版」「文書の組」「研究の全体像との関係」が無ければ、論旨の作業として足す（下の 10 と一緒に切り出す）。
9. **元の場所を正本として指しているものを、すぐ直す。** 段 2 の残りの項目のあいだも、古い写しが正本として使われ続けないようにするため。
   - コードのリポジトリの `CLAUDE.local.md` の「正本を移したもの」に、元の場所と、ハブの中の場所を書く。
   - 個人の記憶とスキル（スキルの既定のパスを含む）のうち、元の場所を指しているものを研究者に一覧で示し、直すか消すかを決めてもらう（記憶の分け方の全体は `imp-current`）。
10. 取り込んだ文書に変更履歴の節や版ごとの注記があれば、現在の内容だけに書き直す作業を、論旨の作業として切り出す（`harness-dispatch`）。中身を変える作業なので、導入の中では行わない。

**Windows のパスを含む文書を書くとき**：シェルのヒアドキュメントを通すと、`\U` などがエスケープとして壊れることがある。ファイルを書く道具（Write）で書く。

### 5.3 組み立てる

**用語集（`hub/glossary.md`）**。材料は次のもの。

- 論旨の文書の「用語」の節
- 修正済みの文字起こしの「主な誤認識の修正」の表
- 個人の記憶の中の用語の決定
- 人名・機材名・ソフト名

出典の列には、どのファイルから取ったかを書きます。

**文献の一覧（`literature/index.md`）**。

- 材料は、文献の調査の記録にある原文の一覧と、論旨の正本の参考文献。
- 書くのは、文献を特定する情報だけ。要約・引用・抜き書きは写さない。
  - 書誌
  - DOI・URL
  - 入手の状態
  - 手元の写しの場所
  - 話題
- 同じ文献が複数の話題に出たら、1 行にまとめる。

**導入前の経緯（`records/history/<始め>_<終わり>_導入前の経緯.md`）**：`harness-progress-timeline` の手順で、次の材料から組み立てる履歴の記録です。

- git のログ（論旨、コード）
- 論旨の変更履歴
- `chats/` の日付
- Claude Code の履歴

時期ごとの表、方針転換の一覧、日付ごとの詳細を書きます。先に研究者に見せ、直してもらってから書きます。

**現在の決定（`hub/decisions.md`）**。材料は次のもの。

- 論旨の変更履歴
- 指導教員のレビュー・会話
- 個人の記憶の中の決定

**いまも有効な決定だけ**を、話題ごとに書きます。

- 各決定に、理由、根拠（ファイル）、決めた人を付ける。
- 置き換えられた決定、取り下げた決定は書かない（導入前の経緯に入る）。
- いまも有効かが分からないものは、研究者に聞く。
- 「会話」の欄に、決めた会話の要約の「決まったこと」の印へのリンクを書く（要約は `imp-sessions` で先に書いてある）。見つからない決定は「不明」とする。

**相談の記録（`records/meetings/<日付>_<題>/README.md`）**。

- 見せたもの（確認用の資料、スライド）と、その後のレビュー・会話を、日付で組にする。作り方とつなぎ方は `harness-meeting-record` に従う。
- `imp-papers` で場所を控えた、git の外の見せた資料（確認用の PDF など）を、その相談の記録に写す。
- 組にできないものは、片方だけで作り、「対応する〇〇は不明」と書く。
- どの相談にも当たらない文字起こし（一人で録ったメモ、指導教員から届いた文書など）は、冒頭に「- 相談の記録：なし」の行を足す。

**実験の記録（`records/experiments/<id>/README.md`）**。

- 材料は、仕様書・検証記録・ログの所在。
- 実験の id は `exp-` で始める（例：`exp-pilot`。記録どうしのリンクが名前で探すため）。
- 実験の目的が論旨のどこに当たるかは、論旨の文書から取る。取れなければ研究者に聞く。

**作業の一覧（`hub/workstreams.md`）**。

- 進行中の作業を 1 行ずつ書く。材料は、開いているブランチ、最近のセッション、未完の実装。
- 完了しているものは書かない（導入前の経緯に残る）。

**個人の記憶の分け方**。個人の記憶や指示を、次のどれに写すかの案を表で出し、研究者が選びます。写した後も、元の記憶は研究者の判断で残すか消します。

| 写し先 | 写すもの |
|---|---|
| `hub/rules.md` | 書き方・運用の決まり。だれが使ってもよい形に書き直す |
| `hub/decisions.md` | 研究の中身の決定 |
| `hub/glossary.md` | 用語の決定 |
| `hub/profile.md` | 場所・道具・秘密 |
| 写さない | 個人の好み、その場限りのもの |

**研究者が使っているスキル**。個人のスキル（`~/.claude/skills/` など）に、この研究のためのものがあれば、どう扱うかの案を表で出し、研究者が選びます。

- `base-` のスキルと同じ役目のもの（例：指導教員に見せる資料を作るスキル）：研究独自のスキルとして `.claude/skills/<名前>/` に写し、`base-` の方を `off` にする。手順は README の「研究に合わせて直す」（元が個人のスキルなら、3 の「`base-〇〇` を元にした」は「個人のスキル〇〇を元にした」と書く）。
- `base-` に無い役目のもの：研究独自のスキルとして写すか、個人のスキルのまま使う。
- `harness-` のスキルと同じ役目のもの：写さない。ハブの仕組みと二重になるため。違いがあれば、`hub/rules.md` や `hub/templates/` に入れられるかを研究者と決める。
- 写した後、元の個人のスキルを残すか消すかは研究者が決める。

**会話の記録（`records/sessions/`）**。

- 研究に関係する作業ディレクトリ（論旨の文書のリポジトリなど。`claude_history.py --list` で探す）を、研究者に確かめて `hub/session-sources.txt` に足す。足さないと、その会話は残らない。
- `harness-session-archive` のスクリプトで、研究に関係する過去の会話の生の記録と読める形を残し、要約のひな形を作る。研究と関係ない会話があれば、研究者に聞いて `hub/session-sources.txt` で除く。
- 過去の会話の要約を書く（書き方は `harness-session-archive`）。会話が多いときは、研究者に、全部を書くか、主な会話だけにするかを聞く。
- 主な会話だけを要約するなら、残りの要約のファイルに「- 要約した範囲：要約しない（理由）」と書く。

**記録どうしのリンク**。

- 相談・実験・会話の要約の「関連」の欄に、分かる範囲でリンクを書く。例：相談 → その相談を受けた会話と扱った実験、実験 → 決めた会話と実装した会話。
- `harness-record-links` を動かして、逆向きのリンクと一覧を作る。切れたリンクを直す。

**現在地（`hub/state.md`）**。上のものから 1 ページにまとめ、研究者に確かめます。

### 5.4 確かめる

研究者に、次のものを見せて直してもらいます。

- 現在地
- 現在の決定の一覧と、履歴に回した古い決定の一覧
- 導入前の経緯の時期ごとの表
- 用語集の件数と、主な追加

## 6. コードのリポジトリとつなぐ

登録したコードのリポジトリごとに、研究者に確かめてから行います。

1. そのリポジトリの直下に `CLAUDE.local.md` を置く（`harness/templates/claude-local.md` から）。
   - 既に `CLAUDE.local.md` があれば、上書きせず、末尾に足すかを聞く。
2. そのリポジトリの `.git/info/exclude` に `CLAUDE.local.md` を足す。
   - `.gitignore` は変えない。公開のリポジトリに、ハブの存在やパスを残さないため。
3. そのリポジトリの作業ディレクトリを、`hub/session-sources.txt` に 1 行足す。そこで開いた会話を、会話の記録の対象にするため（足さないと、その会話は要約も、決定とのつながりも残らない）。

## 7. 仕上げ

1. 進行中の研究なら、段 2 が残っていることを `hub/state.md` に書く（下の 3 で研究者に伝える）。
2. ハブの初回のコミットをする。変えたファイルだけを名前で指定する。
3. 研究者に、次の三つを伝える。
   - **次にすること**：ハブのフォルダで新しいセッションを開くと、それが統括役になる。導入に使ったセッションは閉じてよい。
   - **最初の頼み方の例**：「現在地を説明して」「〇〇の実装を別セッションで進めたい」「次の相談の準備をしたい」
   - **取り込まなかったもの・未決のまま残した項目**：一覧で示す。
   - 進行中の研究なら：段 2 が残っていること。ハブのフォルダで新しい会話を開いて「導入の続きをしたい」と頼めば、統括が作業の一覧の次の項目から進めることを伝える。

## 追加で取り込むとき

導入の後に資料を足すときは、5 の該当する種類だけを行います。現在の文書は、足した資料を入れても現在の内容になるように書き換えます。経緯は `records/history/` とコミットの説明に書きます。
