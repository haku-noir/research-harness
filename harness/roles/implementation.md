# 実装の作業の手引き

実験のシステムや道具を作る作業です。作業の場所は、たいていハブの外のコードのリポジトリです。

## 仕様を先に

- **仕様書から始める。** 実装の前に、作業の場所に仕様書（例：`docs/<名前>_spec.md`）を書くか、既存の仕様書への追補を書く。
  - 研究上の背景は書かない。背景は、ハブの指示書と論旨にある。
  - 仕様書には、実装に要る範囲だけを書く。
- **「決めたこと」の表を置く。** 仕様書の冒頭に置き、聞いて決まったことを、だれが決めたかと一緒に書く。自分で置いた値（初期値、仮の定数）は、自分で置いたと書く。決定が変わったら表を書き換え、前の決定はコミットの説明に書く。
- **仕様の穴は質問する。** 黙って補完しない。
- 判断の優先順位や、検証の進め方の決まりがあれば、`hub/rules.md` に従う。

## 検証

- **自動テスト**：仕様の項目ごとに対応させる。わざと誤らせると失敗することも確かめる。
- **検証記録を書く。** 検証記録（例：`docs/<名前>_verification.md`）には、次を分けて書く。
  - **確かめたこと**（証跡のパス）
  - **実際の環境（装置、参加者、本番のデータなど）でしか確かめられないこと**（方法の例と、未確認であること）

  自動テストの成功を、実際の環境で確かめた印として扱わない。

## git

- **コードのリポジトリへのコミットは、研究者の指示か、プロフィールの方針に従う。** 既定は「頼まれたときだけ」。ハブへのコミット（報告、記録）は、共通の手引きの「コミットする」。
- **ブランチを切ってからコミットする。** 機能ごとにコミットする。
- **自分が変えていないファイルは、コミットに含めない。** 作業前からあった未コミットの変更や未追跡のファイルは、報告に書く。
- **既定のブランチへのマージや push は、研究者の指示があるときだけ。**

## 実験とのつながり

- 指示書が実験の id を示していれば、`<hub>/records/experiments/<id>/README.md` の「実装」の表に 1 行足す。版、ブランチ・コミット、仕様書、検証記録を書く。
- ログの形を変えたら、版の番号（アプリの版など）を上げる。解析の側がログを見分けられるようにするため。
