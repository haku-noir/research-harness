# 研究の流れ

このハーネスが想定している研究の進め方です。統括のセッションは、いまどの段にいるかをこの流れで判断します。どの段も、順番どおりに一度だけ通るのではなく、指導教員との相談のたびに回ります。

## A. 論旨の流れ（主な流れ）

論旨は論文ごとに組む（`papers/<論文の id>/`）。論文をまたいで持ち続ける研究の全体像は `hub/research.md` にある。

0. **論文を始める**：研究の全体像から、この論文で扱う問いを選び、論文の種類と文書の組を決めて `papers/<論文の id>/` を作る（研究者が決める）。
1. **入力**：指導教員の発言を記録する。
   - 会話の文字起こし、思いつきのコメント、文書へのレビュー、ゼミの議事録。
   - → 文字起こしのスキル（`base-transcript-fix` か、研究で置き換えたもの）で `chats/` に置き、用語集を育てる。
   - → `harness-meeting-record` で相談の記録につなぎ、決定の候補を研究者に示す。
2. **把握**：指導教員の発言を整理し、いまの論旨とのずれを示す。
   - 統括のセッション。新しい発言を、すぐに論旨には入れない。
3. **詰める**：論点を詰める（議論の進め方は `harness/base-rules.md` と `hub/rules.md`）。
   - → 論旨の作業（`harness-dispatch`、手引き `harness/roles/argument.md`）。
4. **調べる**：先行研究の原文を集め、各研究の論点と課題設定で整理する。
   - 取れない文献は、URL・保存先・ファイル名を示して研究者に頼む。
   - → 文献の作業（`harness/roles/literature.md`）。
5. **反映する**：論文の論旨の正本を更新する。
   - 版をそろえ、現在の内容だけに書き換え、未決事項を残す。経緯はコミットの説明に書く。大きく変わるならブランチを切る（`harness/roles/argument.md` の「大きな改訂のブランチ」）。
   - 論文をまたぐこと（新しく分かったこと、研究の問いの変化）は、研究者が決めてから `hub/research.md` に書く。
6. **点検する**：
   - 新しい論点が、いまの論点と混ざっていないか確かめる。
   - 前に見せた版から何が変わったかを分けて示せるようにする。
   - 別の目で読ませるなら、レビューの作業を切り出す。観点と渡す情報は、統括が案を出して研究者が決める（`harness/roles/review.md`）。
7. **見せる**：
   - 確認用の資料 → 確認用の資料のスキル（`base-review-export` か、研究で置き換えたもの）
   - 発表資料 → 発表の作業
   - 見せる前に → 相談の準備のスキル（`base-meeting-prep` か、研究で置き換えたもの）で、前回からの進みと聞くことをまとめる
   - 見せたもの → `harness-meeting-record` で相談の記録に残し、見せた版にタグを付ける
8. **レビューを受ける** → 1 に戻る。
   - レビューで出た書き方の決まりは `hub/rules.md` に足す。
   - 方針転換は `hub/decisions.md` を書き換えて反映し、前の決定と理由をコミットの説明に書く。
9. **書き終える**：提出・発表が済んだら、その論文の論旨は読み出しのみにする。分かったことを、研究者が決めて `hub/research.md` の「これまでに分かったこと」に書く。次の論文は 0 から。

## B. 実装と実験の流れ（論旨から切り出す）

1. **切り出す**：論旨のどこを確かめるための実装・実験かを決め、指示書を書く（`harness-dispatch`）。
2. **仕様**：実装に要る範囲だけを仕様書にする。不明点は質問し、決まったことを仕様書の表に残す。
3. **実装と検証**：自動テストと検証記録を用意する。
   - 実際の環境でしか確かめられないことは、確かめたことと分けて記録する。
4. **git**：ブランチを切り、機能ごとにコミットする（方針に従う）。
5. **実施**：実験を実施し、手順や使い勝手の修正を往復する。
   - 実施した回とデータの所在を `records/experiments/` に書く。
6. **解析**：解析の作業を切り出す。図と数値を、スクリプトのコミットと一緒に `records/experiments/` に残す。
7. **報告**：`hub/reports/` に書く。統括が証跡を確かめて記録し、論旨の流れに結果を戻す。

## C. 試行（本流に入れる前に確かめる）

- **使う場面**：入れるべきか迷う案、結果しだいで論旨の優先順位が変わる案。
- **進め方**：
  1. 試行として切り出す（`harness-dispatch`、手引き `harness/roles/trial.md`）。
  2. 本流を変えずに早く確かめる。
  3. 結果を見て、本流に入れる・別に残す・捨てるを決める（`harness-merge`）。

## つなぎ目

- **見せる → 話す → 記録する → 対応する → 次に見せる**：相談の記録（`records/meetings/<日付>_<題>/`）を軸に、次のようにつなぐ。
  1. 見せた資料を相談の記録に残し、見せた版にタグを付ける（`harness-meeting-record`）。
  2. 文字起こしを `chats/` に置き、同じ相談の記録につなぐ。決まったことは研究者が確かめてから `hub/decisions.md` へ。
  3. 指摘に対応する作業の指示書の「関わる相談」に、相談の記録と文字起こしを書く（`harness-dispatch`）。報告の「関連」にも書く。
  4. 相談の記録の末尾に、対応した作業・決定・会話が自動で並ぶ（`harness-record-links`）。次の相談の準備では、そこから「前回の指摘への対応」を作る。
- **相談 → 優先順位の変化 → 実装**：相談で論旨の優先順位が変わり、その結果として予備実験が要る、という流れはよく起きる。統括は次のように動く。
  1. 方針転換を `hub/decisions.md` に反映する（前の決定はコミットの説明へ）。
  2. 進行中の作業のうち、影響を受けるものを止めるか直すかを研究者に聞く。
  3. 新しい作業を切り出す。
- **実験の結果 → 論旨**：論旨に戻すときは、次の順に進める。
  1. 解析の記録（事実と解釈を分けたもの）を論旨の作業に渡す。
  2. 主張にするか、予備実験にとどめるかを研究者が決める。
- **いつでも**：`harness-progress-timeline` で、日付ごとの進捗と方針転換を、git の履歴と `records/` から確かめられる。
